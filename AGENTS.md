# Instruções para agentes de IA (Copilot, etc.)

Este arquivo define como assistentes de IA devem trabalhar neste repositório.
Leia-o **antes** de qualquer ação.

## 🚫 O Copilot NUNCA pode aparecer como autor ou contribuidor

O único autor de todos os commits deste repositório é **Blima-P**. Por isso:

- **Nunca** incluir `Co-authored-by: Copilot ...` (nem qualquer outro `Co-authored-by`) em mensagens de commit,
  descrições de PR ou comandos sugeridos ao usuário. Essa linha faz o GitHub listar o Copilot em *Contributors*.
- **Nunca** sugerir mensagens com "Generated by Copilot", "🤖", assinaturas de IA ou similares.
- Mensagens de commit sugeridas devem conter **apenas** o título no padrão Conventional Commits
  (e, se necessário, um corpo descritivo), sem *trailers*.
- Antes de passar comandos de push, o agente pode conferir (somente leitura) se algum commit tem *trailer*:

```powershell
git --no-pager log origin/main..HEAD --format="%h %s%n%(trailers:only,unfold)"
```

## 🚫 Regra principal: o agente NÃO executa operações de Git/GitHub

O dono do repositório faz **todos** os commits, pushes e PRs manualmente.
O agente **não pode** executar comandos que alterem o histórico, as branches ou o repositório remoto:

- `git commit`, `git push`, `git merge`, `git rebase`, `git reset`, `git revert`, `git tag`
- `git checkout -b` / `git switch -c` / `git branch` (criar, trocar ou apagar branches)
- `git add` / `git rm` / `git stash`
- `gh pr create`, `gh pr merge`, `gh issue create` ou qualquer ação que escreva no GitHub

**Permitido** (somente leitura): `git status`, `git log`, `git diff`, `git branch --show-current`, `git remote -v`.

### O que o agente deve fazer no lugar

Ao terminar uma alteração, o agente deve **entregar ao usuário os comandos prontos**, com comentários
explicando cada passo. Exemplo:

```powershell
# Nova branch
git switch -c feat/nome-da-feature

# Confere o que mudou
git status

# Salva as mudanças
git add -A
git commit -m "feat(escopo): descrição curta"

# Manda pro GitHub e abre o PR
git push -u origin feat/nome-da-feature
gh pr create --base main --title "feat(escopo): descrição" --body "O que foi feito, em poucas linhas."
```

### Conta do GitHub

Este repositório pertence à conta pessoal **Blima-P** (`https://github.com/Blima-P/InvestStart`).
A máquina também tem a conta de trabalho `pedroblima_caesb` logada no `gh`, e o `gh` é o
*credential helper* do git, então o push sai pela **conta ativa** do `gh`.

Antes de passar comandos de push/PR, o agente deve verificar (somente leitura) e avisar o usuário se
a conta ativa ou o e-mail do repositório estiverem errados:

```powershell
gh auth status                 # conta ativa deve ser Blima-P
git config user.email          # e-mail local do repositório (não o da CAESB)
```

Comandos que o **usuário** roda para ajustar:

```powershell
gh auth switch --user Blima-P            # antes do push/PR
gh auth switch --user pedroblima_caesb   # depois, para voltar à conta de trabalho
```

Junto com os comandos, o agente deve sugerir:
- nome da branch (`feat/<nome>`, `fix/<nome>`, `docs/<nome>`)
- mensagem de commit ([Conventional Commits](https://www.conventionalcommits.org/pt-br/))
- título e descrição do PR

## 🛠️ Boas práticas

### Escopo
- Uma tarefa por vez e um PR por item do plano.
- Não fazer melhorias, refatorações ou "aproveitei e arrumei" sem o usuário pedir. Sugira e espere.
- Dúvida de regra de negócio ou de arquitetura: pergunte antes de implementar.

### Testes
- Testes **nunca** chamam APIs reais (brapi, BCB, CoinGecko, Tesouro). Use respostas simuladas (mock).
- Guarde exemplos de respostas reais em `backend/tests/fixtures/` para usar nos mocks.
- Teste também o caminho de erro: API fora do ar, resposta vazia, dado inválido.

### Regras de negócio
- Percentuais, limites e pesos das regras (RN02, RN05, RN06, RN07) ficam em configuração,
  nunca soltos no código. Exemplo: `MAX_CRIPTO = 0.10`, não um `0.1` perdido num `if`.
- Toda regra implementada deve ter teste com o caso limite (ex.: cripto exatamente em 10%).

### Código
- Type hints em todas as funções.
- Funções pequenas, com um único objetivo.
- `logging` em vez de `print`.
- Nunca registrar tokens, chaves ou dados pessoais nos logs.
- Erros de fontes externas são tratados: usar o último dado válido e avisar (RN08).

### Dependências
- Antes de adicionar uma biblioteca, pergunte ao usuário e explique por que ela é necessária.
- Prefira a biblioteca padrão do Python ou o que já está no projeto.
- Toda dependência nova vai no `pyproject.toml` (backend) ou `package.json` (frontend).

### Decisões
- Decisão importante (biblioteca, arquitetura, mudança de regra) ganha uma entrada em
  [docs/DECISOES.md](docs/DECISOES.md): o que foi decidido e por quê, em poucas linhas.

### Versionamento
- [SemVer](https://semver.org/lang/pt-BR/): `MAIOR.MENOR.CORREÇÃO`. Enquanto estiver em `0.x`, o projeto é considerado em desenvolvimento.
- Cada fase concluída do plano aumenta o número do meio: Fase 0 → `v0.1.0`, Fase 1 → `v0.2.0`, etc.
- A versão fica em `backend/app/__init__.py`, `backend/pyproject.toml` e, quando existir, `frontend/package.json`.
- Ao fechar uma fase, passe ao usuário os comandos da tag:

```powershell
# Marca a versão e manda pro GitHub
git tag -a v0.1.0 -m "Fase 0 concluída"
git push origin v0.1.0
```

## ✍️ Estilo de comentários e textos

Escreva como uma pessoa escreveria, não como um robô. Vale para comentários no código,
comandos passados ao usuário, mensagens de commit, descrições de PR e documentação.

- **Curto e direto:** uma linha sempre que der. Se precisa de um parágrafo, o código provavelmente precisa ser mais claro.
- **Comente o porquê, não o óbvio:** nada de `# importa o FastAPI` ou `# retorna o resultado`.
- **Linguagem natural:** "Manda pro GitHub" em vez de "Realizar o envio das alterações para o repositório remoto".
- **Sem siglas internas nos comentários de código** (RN01, RNF05...) — elas ficam nos docs.
- **Sem enfeite:** nada de emojis, "✨", "🤖" ou textos de marketing em código e commits.
- **Commits e PRs:** título curto no Conventional Commits; corpo só se acrescentar algo útil.

Exemplos:

```python
# Ruim
# Esta função é responsável por realizar o cálculo do score do ativo conforme a RN05
# Bom
# Score maior = melhor relação retorno/risco
```

```powershell
# Ruim
# 4. Realizar o commit das alterações seguindo o padrão Conventional Commits
# Bom
# Salva as mudanças
```
